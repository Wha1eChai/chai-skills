# Skill Maintenance and Learning

Read only when maintaining this skill, evaluating its routing, or promoting a transferable lesson. Ordinary UI tasks do not load this document. Source adaptation also uses [Provenance](provenance.md).

## What belongs where

- Business facts, routes, local exceptions, selected visual directions: existing project documentation.
- Stable project design conventions: its DESIGN.md or equivalent, linked to authoritative tokens/components.
- Machine values: the existing token/theme source, not a copied table in several documents.
- General decision methods with applicable conditions: this skill, after scoped maintenance is requested.
- Task evidence: the project's appropriate test/report location or a concise result, not a new permanent rule.

Do not automatically write memory after every change. A reusable lesson should identify the trigger, observed problem, reasoning, recommended approach, exceptions, and evidence or hypothesis status. Retire contradicted rules rather than indefinitely appending caveats.

Research and live user evidence can improve confidence over time, but are not prerequisites for first use. Do not claim fewer corrections or better design results before observing them.

| Make the same-brand guide more expressive | Load Case 2; vary scale, weight, and rhythm while holding content/identity | Assumes expression requires a new font, palette, or oversized hero |

## Outcome-led expression desk review

| Request | Expected behavior | Failure signal |
| --- | --- | --- |
| Make a documentation palette more vivid while preserving the brand | Identify anchors and open color relationships; improve palette character, hierarchy, and reading comfort within scope | Automatically changes only text brightness or freezes every existing color value |
| Make a dashboard visually appealing | Develop clear states/actions together with suitable type, color, imagery, and detail | Treats Operate as mandatory gray, quiet, or low-saturation styling |
| Improve contrast with ambiguous feedback | Consider readability, hierarchy, and palette character using available context; recommend or narrowly clarify | Assumes contrast only means a numerical text ratio |
| Create an appealing direction outside the five example cases | Use relevant reasoning and additional project/supplied references to form a fitting approach | Treats examples as an exhaustive menu or a one-case ceiling |
| User now prefers a stronger expression | Describe the updated preference and adapt the design | Retroactively labels the earlier valid aesthetic a proven usability defect |
| Supporting labels pass contrast thresholds but remain difficult to scan | Inspect rendered comfort and hierarchy; improve the relevant relationships | Treats minimum numerical compliance as complete visual acceptance |
| Expressive typography reveals a better arrangement | Revisit composition while preserving task and content requirements | Treats structure and expression as a rigid one-way sequence |

## Maintenance workflow

1. Read the affected entry/reference and source rationale; identify the actual ambiguity or failure.
2. Change the smallest ownership/routing boundary that resolves it. Prefer positive experience goals and concrete design moves for aesthetic guidance; retain explicit constraints for safety, truthfulness, accessibility, and authorization. Check whether a supposed universal rule is actually a style preference, example-specific choice, or implementation shortcut. Avoid copying a rule into several references.
3. Check affected scenarios above for trigger, order, artifact, and stop behavior. Add a scenario for a new failure class.
4. Check frontmatter, relative links, file names, code fences, and formatting. Confirm execution guidance does not require maintenance documents.
5. Report structural checks and manual scenario review separately. Do not present either as a runtime loading test or a measured generation-quality benchmark.

Keep the declared name `interface-design` aligned with its directory unless a rename is explicitly requested. If references move, update callers and validate links. Do not auto-install or re-register a revised skill as part of ordinary maintenance.
